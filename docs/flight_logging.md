# Shared flight logging

Both the H723 application and F405 application can use the C11 API in
`common/include/flight_common/log.h`, linked through `Flight::Common`.
`Autopilot::Core` and `Flight::IO` already expose that dependency. The libraries
do not log automatically: the application records their inputs, results, and
faults at a chosen rate. Existing JSBSim CSV logging is unchanged.

```text
H723: estimator / autopilot results -> flight_log_emit -> H723 firmware queue
F405: RC / supervisor / PWM demands -> flight_log_emit -> F405 firmware queue
                                                             |
                                             background flash writer
                                                             |
                                      raw dump -> decode_flight_log.py -> CSV
```

The codec is implemented. Queues, flash drivers, and download commands are planned
parts of this project's H723/F405 firmware implementation. A shared format does
not require shared physical storage. Each MCU can log
locally, or F405 records can be forwarded intact to an H723 storage worker. If
forwarded, retain their F405 source/session/time and recognize that H723 failure
can prevent storage of those records. Local I/O storage preserves more evidence
of a main-controller failure, provided its own power and hardware remain healthy.

## Firmware interface

```c
#include "flight_common/log.h"

/* Implement this in firmware: bounded, complete COPY into your queue.
 * Return false without accepting bytes if the queue cannot fit the record.
 * Never retain 'bytes': it refers to temporary memory owned by the codec. */
bool board_log_enqueue(void *queue, const uint8_t *bytes, size_t length);

flight_logger_t logger;
/* During startup: check the return, use a new nonzero boot/session ID. */
bool ready = flight_log_init(&logger, FLIGHT_LOG_H723, boot_session_id,
                             board_log_enqueue, &board_queue);

/* After a successful ap_step(): */
flight_log_entry_t entry = {0};
entry.type = FLIGHT_LOG_CONTROLS;
entry.data.controls.values = ap_result.controls;
entry.data.controls.stage = FLIGHT_LOG_COMPUTED;
entry.data.controls.valid = true;
flight_log_result_t result = flight_log_emit(&logger, sample_time_us, &entry);
/* ACCEPTED means queued, DROPPED means queue rejection, INVALID means API error.
 * Handle/report errors outside control execution; never retry until it blocks.
 * Do not mark old ap_result values valid when the controller call failed. */
```

On F405, initialize another logger with `FLIGHT_LOG_F405`, its own boot/session
ID and its own local clock. Use `FLIGHT_LOG_PILOT` for calibrated RC commands,
`FLIGHT_LOG_SELECTED` for supervisor outputs, and `FLIGHT_LOG_IO` for status,
RC/AP ages, saturation, and final PWM demands. Fill I/O records from the current
supervisor/mapping results; do not fabricate fresh outputs after a failed call.
`tests/log_core_test.c` is an executable example using actual calls to both
libraries and one copying RAM sink in place of firmware storage.

One producer owns each logger. The logger is not internally synchronized;
serialize calls from different tasks or collect events into one logging task.
Do not call it concurrently from an ISR and a task. It allocates no heap and
uses bounded record buffers, but the callback must enforce the nonblocking
contract. No flash operation belongs inside that enqueue callback.

Record timestamps refer to the sampled value/decision, not the later flash-write
time. Firmware supplies monotonic **64-bit microseconds since boot**, extending
any wrapping hardware timer. A source/session pair identifies one clock domain.
Never compare raw H723 and F405 timestamps as though they share a clock.

At boot, emit `BOOT` with identifiers for the firmware build, configuration, and
reset reason. Keep the corresponding build/configuration files on the PC; those
IDs do not contain the full configuration. Firmware assigns a new nonzero session
ID every boot and must avoid reuse in retained logs (e.g. a persistent boot
counter with defined rollover handling). Neither boot IDs nor timestamps are
generated by this library.

`CLOCK_PAIR` can record a firmware-estimated correspondence between a local
timestamp and a peer timestamp/session, including uncertainty. Merely recording
packet reception time alongside its remote send time ignores link latency.
A clock exchange/estimator is still needed; log multiple pairs to estimate drift.
The decoder preserves them but does not automatically align the clocks.

## Binary format: FLG1 version 1

Records are concatenated with no required file header. All integers and IEEE-754
binary32 floats are little-endian. Each record has a 32-byte header, a typed
payload, and four CRC bytes. Explicit encoding avoids C padding, enum size, and
compiler ABI dependence. Do not store a raw `flight_log_record_t` memory image.

| Header offset | Bytes | Meaning |
| --- | --- | --- |
| 0 | 4 | ASCII `FLG1` magic |
| 4 | 1 | Format version, 1 |
| 5 | 1 | Source: 1 H723, 2 F405, 3 simulator |
| 6 | 2 | Record type |
| 8 | 2 | Payload length, at most 64 |
| 10 | 2 | Reserved, zero |
| 12 | 4 | Sequence of valid logging attempts, modulo 2^32 |
| 16 | 4 | Nonzero boot/session ID |
| 20 | 8 | Source-local sample time in microseconds |
| 28 | 4 | Cumulative enqueue rejections, saturating at UINT32_MAX |
| 32 | N | Payload |
| 32+N | 4 | CRC-32/ISO-HDLC of header + payload |

CRC parameters: reflected polynomial `0xEDB88320`, initial value `0xFFFFFFFF`,
final XOR `0xFFFFFFFF`; same result as Python `zlib.crc32`.

| Type | Payload bytes | Wire fields in order |
| --- | --- | --- |
| 1 BOOT | 12 | firmware_id u32, config_id u32, reset_reason u32 |
| 2 CONTROLS | 20 | aileron/elevator/rudder/throttle f32, stage u8, valid u8, zero u16 |
| 3 STATE | 40 | roll/pitch/yaw f32, p/q/r f32, true airspeed/altitude/climb rate f32, valid_fields u32 |
| 4 IO | 32 | authority/reason/pulse_count/armed u8, rc_age_ms/autopilot_age_ms/saturated_mask u32, eight pulse_us u16 |
| 5 EVENT | 12 | code u16, severity u8, zero u8, argument0/argument1 u32 |
| 6 CLOCK_PAIR | 20 | peer_source u8, three zero bytes, peer_session_id u32, peer_timestamp_us u64, uncertainty_us u32 |

Controls use the shared logical conventions: surfaces [-1,1], throttle [0,1],
positive aileron for right roll and negative elevator for nose-up. Stage is
1 computed, 2 pilot, 3 selected. The logger preserves nonfinite/out-of-range
values for diagnosis; it is not a control-input validator. Set validity honestly.
STATE units match `ap_state_t`: radians, rad/s, m/s, meters MSL, positive-up climb.
Bits 0..8 of `valid_fields` identify usable state fields in wire order.

IO authority: 0 disarmed, 1 manual, 2 autopilot, 3 failsafe. Reason: 0 disarmed,
1 pilot request, 2 auto active, 3 RC unavailable, 4 autopilot unavailable,
5 re-engagement required. Pulse count is 0..8, unused pulse slots are zero,
and saturation bits can only refer to active slots. Unavailable sample ages use
UINT32_MAX. Pulse widths are demands, not measured actuator positions; armed
reflects firmware permission, not measured electrical state.

Event severity is 0 info, 1 warning, 2 error. Event codes and integer argument
meanings belong to the application/build's event dictionary. The initial schema
does not yet define raw IMU/GNSS, mission tracking, or controller-setpoint records.
Add documented typed records when those producers are integrated. C rejects
unknown versions/types; the PC decoder retains unknown v1 payloads as hex while
validating framing and CRC. Changes to an existing payload require a new type or
format version, not silently reusing its ID.

## Storage responsibilities and failure recovery

Every valid enqueue attempt consumes a sequence number, including queue-full
rejections. The next accepted record carries the updated drop total. API/schema
errors do not consume sequence numbers. A gap indicates missing attempts;
it does not prove whether loss happened at enqueue, writing, or extraction.
Queue drops at the end of a log cannot appear in a later record if none survives.
Firmware must separately track flash-worker errors; the library's drop counter
counts only rejected enqueues, not later persistence failures.

The background worker owns page alignment, programming granularity, sector erase,
capacity management, write verification, and durable write/commit tracking for
the chosen flash chip. Prefer preparing storage before arming. Size the queue
for the longest writer stall; choose log rates from measured control-loop timing
and available storage. CRCs detect damaged records but do not make flash writes
atomic. Following a reset, do not append into a partially programmed area;
recover a valid append location or start a fresh prepared segment.

As an example budget, a 76-byte STATE and 56-byte CONTROLS record at 50 Hz cost
6,600 bytes/s on H723. A 68-byte IO and 56-byte CONTROLS record at 50 Hz cost
6,200 bytes/s on F405. Together that is 46.08 MB per hour before events, metadata,
page padding, or storage overhead. These are example rates, not flight defaults.

After disarm, drain the queue and complete/verify pending writes before declaring
the log saved. Firmware also implements the download path (USB/UART/debugger or
removable storage). A dump should be a stable snapshot, not memory being modified
while it is downloaded. Circular storage needs firmware segment/generation
metadata to recover ordering after wrap; this record codec is not a flash
filesystem and the decoder does not infer circular-buffer chronology.

## Post-flight retrieval on the PC

After firmware exports a raw dump or record stream:

```powershell
python tools/decode_flight_log.py h723.bin f405.bin --output flight.csv
```

The tool uses only the Python standard library, maps files rather than loading
whole dumps into RAM, and refuses to overwrite an existing output file. Each CSV
row includes the input file and byte offset, source/session, timestamp, sequence,
drop total, and decoded fields. It preserves input-file and record order; it does
not merge independent clocks. CSV fields for other record types are empty.

The scanner checks magic/version/length/CRC and known payload schemas, skips
erased gaps or corrupt records, and recovers subsequent complete records after a
torn write. It reports skipped bytes (including erased space) and invalid/torn
candidates. Skipping damage recovers evidence, not proof that a log is complete.
Exit status is 0 with recovered records, 1 for file/OS errors, and 2 if no valid
records were found; inspect the diagnostics even when the exit status is zero.

Validation includes independent golden bytes, all record types, invalid payloads,
single-bit corruption, truncation, queue rejection, sequence wrap, counter
saturation, records from both libraries, and a C-to-Python-to-CSV integration.
No physical flash, download transport, timing deadline, or power-cut test is
claimed by these host tests.
